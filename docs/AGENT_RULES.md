# Agent Rules — vista-ui Component Library

> MANDATORY reading before touching any component code. These rules exist because we learned them the hard way.

---

## Rule 1: Read landing2 source BEFORE writing any code

The reference implementation lives at `/root/clawd/vistawtf/landing2/src/`.

Before editing any component:
1. Find the equivalent component in landing2
2. Read its source line by line
3. Copy exact values — no guessing, no creative interpretation

Key files to read:
- `landing2/src/app/globals.css` — all design tokens
- `landing2/src/components/sections/Navigation.tsx` — navbar reference
- `landing2/src/components/sections/HeroSection.tsx` — hero reference
- `landing2/src/components/sections/FooterSection.tsx` — footer reference

---

## Rule 2: Never use Tailwind classes for layout-critical spacing on library components

Tailwind v4 does NOT scan `node_modules/@vistawtf/ui/dist/` by default. Any Tailwind utility class written inside a library component will silently fail in consumer apps unless the consumer adds `@source "../node_modules/@vistawtf/ui/dist"` to their `globals.css`.

**For layout-critical properties (padding, margin, height, width), use inline styles or CSS classes defined in `src/styles.css`.**

Examples of what breaks silently:
- `pt-[160px]` on a component → renders as 0px in consumer apps
- `md:pt-[180px]` → completely ignored
- `gap-8` → may render as default

**The hero navbar overlap bug was caused by this exact issue.** The `pt-[160px]` class existed in the source but was never generated by Tailwind in the demo app. Fix: use `style={{ paddingTop: '160px' }}`.

**Rule:** If a spacing value is structural (defines layout/clearance), use `style={{}}` or a CSS class in `styles.css`. Only use Tailwind utilities for decorative properties (colors, borders, hover states, transitions) — and add `@source` to any consumer app.

## Rule 3: Every fix to a demo must also fix the library component

When Isaac reports a visual bug in the demo:
1. Fix it in the **library component** (`src/components/`)
2. Update `src/styles.css` if needed
3. Run `npm run build` to rebuild the dist
4. Reinstall in the demo: `cd examples/demo && npm install`
5. Restart the demo server
6. Screenshot and verify

**Never patch only the demo page** (`examples/demo/app/...`). The demo exists to test the library. A demo fix that doesn't fix the library is not a fix.

## Rule 4: Build workflow after any library change

```bash
# 1. Build the library
cd /root/clawd/vistawtf/vista-ui
npm run build

# 2. Reinstall in demo (forces new dist to be picked up)
cd examples/demo
npm install --prefer-offline

# 3. Kill old dev server and restart fresh
pkill -f "next"
node_modules/.bin/next dev --port 3000 > /tmp/demo-dev.log 2>&1 &

# 4. Wait for server to be ready
sleep 10 && curl -s http://localhost:3000 > /dev/null && echo "UP"
```

Skipping step 2 means the demo still uses the old dist.

## Rule 5: Always verify git remote before pushing

```bash
git remote -v
```

Confirm the remote points to `vistawtf/vista-ui` — not any other repo. We accidentally pushed bot.py to `openclaw-easy-setup` because of a misconfigured remote. Never again.

Commit identity:
```bash
git -c user.name="enti-bot" -c user.email="enti-bot@users.noreply.github.com" commit -m "..."
```

## Rule 6: CSS custom properties only — never hardcode hex values

All colors must use CSS custom properties defined in `src/styles.css`:

```
--ultra-orange: #FF5233
--background
--foreground
--surface
--border
--muted
```

Exception: `--ultra-orange` opacity variants don't work with Tailwind `/20` modifier syntax. Use explicit `rgba(255, 82, 51, 0.2)` instead of `var(--ultra-orange)/20`.

---

## Rule 7: Navbar mobile menu = landing2 inline dropdown pattern

The Navbar mobile menu must match landing2's pattern exactly:
- Bordered square button (`border rounded-[3px]`) with lucide `Menu`/`X` icons
- Dropdown appears inline below the navbar bar (NOT a fullscreen overlay)
- Animation: `max-h` transition with `cubic-bezier(0.22, 1, 0.36, 1)`
- Links close the menu on click

Do NOT use fullscreen overlay / drawer pattern for mobile menu.

## Design tokens quick reference

From `landing2/src/app/globals.css`:

```
Font: Geist Sans (headings/body), Geist Mono (labels/code)
Orange: #FF5233 (hover: #E64A2E)
Background light: #FFFFFF
Foreground light: #111111
Muted text: #575757 (body), #999999 (labels)
Border light: black/[0.08]
Transition easing: cubic-bezier(0.16, 1, 0.3, 1) — spring feel
Border radius: 3px (buttons, cards), 2px (small elements)
```

Navbar:
```
Height: py-3 inner (not fixed h-14) — approximately 48px
Horizontal padding: px-4 md:px-16 (16px → 64px)
Background: always solid (never transparent)
Breakpoints: lg: for desktop nav (1024px)
```

Hero:
```
padding-top: 140px (this is the EXACT landing2 value)
padding-bottom: 90px
Max-width content: 560px–640px
```

## Common failure modes

| Symptom | Root cause | Fix |
|---------|-----------|-----|
| Hero content hidden behind navbar | `pt-[XXpx]` Tailwind class not generated | Use `style={{ paddingTop: 'XXpx' }}` |
| Footer renders white instead of dark | Tailwind not scanning dist/ | Add `@source` to consumer globals.css |
| Mobile menu is fullscreen overlay | Wrong pattern used | Match landing2 inline dropdown |
| Styles look different from landing2 | Guessed values instead of reading source | Read landing2 source first |
| Push goes to wrong repo | Remote misconfigured | Always run `git remote -v` first |
